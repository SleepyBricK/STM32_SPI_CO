# Лог изменений агента от 2026-03-18

## Контекст

В рамках этой сессии были изменены компоненты регистрации данных `Intan RHS2116` в проекте:

- `services/server/intan_udp_recorder.py`
- `services/server/intan_tcp_server.py`
- `services/gui/intan_gui_clientv5_linux.py`

Цель изменений:

- ускорить путь поканальной регистрации с учетом использования драйвера `/dev/intan`
- добавить вычисляемые временные метки для каждой точки без изменения UDP-протокола
- исправить экспорт CSV
- убрать EMG-специфичную логику и вернуть широкополосную запись для работы на `40 кГц`

## 1. Оптимизация сервера регистрации

Файл: `services/server/intan_udp_recorder.py`

Сделано:

- Добавлен флаг `self.using_driver`, чтобы не выполнять повторные проверки `use_driver()` в разных местах.
- После инициализации SPI/драйвера закэшированы возможности:
  - `self._spi_has_direct_convert`
  - `self._spi_has_auto_convert`
- В `record_channels()`:
  - список каналов приводится к `tuple`
  - добавлена явная проверка на пустой список каналов
  - режим последовательных каналов вычисляется один раз на старт записи
  - для последовательных каналов используется fast-path через `convert_channel_auto()`
  - добавлен более стабильный pacing через `time.perf_counter()` и `next_sample_deadline`
- Структура `channel_data` упрощена:
  - было: `channel -> {'ac': value, 'timestamp': sample_start}`
  - стало: `channel -> value`
- В `UDPRecorderServer`:
  - добавлен счетчик версии клиентов `self._clients_version`
  - обновление списка клиентов в цикле записи стало событийным, а не на каждом sample
  - убран лишний `print()` из горячего пути
- В `_send_packet()` упаковка адаптирована под упрощенный `channel_data`

Ожидаемый эффект:

- меньше Python-накладных расходов на горячем пути
- лучшее поведение при работе через драйвер `/dev/intan`
- дешевле формирование sample и отправка UDP-пакетов

## 2. Вычисляемые timestamp для каждой точки

Файл: `services/gui/intan_gui_clientv5_linux.py`

Сделано:

- Добавлено поле `self.recording_sample_rate`
- При старте записи частота регистрации сохраняется в GUI
- Во время парсинга UDP-пакетов добавлен расчет времени точки:

```text
point_time = sample_time + i * (1 / (sample_rate * channel_count))
```

где:

- `sample_time` — timestamp sample от сервера
- `i` — индекс точки внутри sample
- `sample_rate` — частота на канал
- `channel_count` — число каналов в sample

Структура данных канала в GUI расширена:

- было: `{'time': [], 'values_uv': []}`
- стало: `{'time': [], 'point_time': [], 'values_uv': []}`

Смысл:

- `time` — время sample, сохранено для совместимости
- `point_time` — вычисленное время конкретной точки внутри sample

График регистрации переведен на использование `point_time`, если оно доступно.

## 3. Исправление экспорта CSV

Файл: `services/gui/intan_gui_clientv5_linux.py`

Сделано:

- старый экспорт предполагал одно общее время для всех каналов и писал:
  - `Время (с)`
  - далее значения всех каналов
- новый экспорт пишет данные по каждому каналу отдельно:
  - `Индекс точки`
  - `<канал> время (с)`
  - `<канал> (µВ)`

Особенности:

- если у канала есть `point_time`, экспорт использует его
- если запись старого формата, используется fallback на `time`

Эффект:

- CSV больше не искажает время точек при последовательном многоканальном опросе

## 8. Важные замечания

- UDP-протокол между сервером и GUI не менялся
- timestamp каждой точки сейчас вычисляемый, а не аппаратный
- сервер по-прежнему отправляет один timestamp на sample
- точность `point_time` основана на предположении о равномерном последовательном опросе каналов
- широкополосные дефолты теперь соответствуют задаче записи, а не EMG-режиму

## 9. Фикс режимов питания и переходов recording <-> stimulation

Файлы:

- `services/server/intan_tcp_server.py`
- `services/server/rhs2116_profiles.py`

Проблема:

- TCP-контроллер по умолчанию инициализировал чип сразу в stimulation mode
- это включало stimulation path через `Register 32 = 0xAAAA` и `Register 33 = 0x00FF`
- после этого даже команды, не связанные со стимуляцией, могли работать на чипе уже в stimulation-ready состоянии
- это создавало риск лишнего потребления по питанию и нежелательной активности VSTIM path

Что изменено:

- `IntanController.ensure_initialized()` теперь выполняет безопасную базовую инициализацию в `recording`-режим, а не в `stimulation`-режим
- добавлены явные методы:
  - `ensure_recording_ready()`
  - `ensure_stimulation_ready()`
- реальные стимуляционные операции теперь явно переводят чип в stimulation mode:
  - `pulse()`
  - `sawtooth()`
  - `execute_pattern()`
- команда `init` теперь переводит чип в безопасный recording mode
- команды `configure_adc` и `configure_filters` теперь тоже выполняются через safe recording mode
- `stop_all()` теперь:
  - выключает triggered-регистры стимуляции
  - пишет `Register 42 = 0x0000`
  - возвращает `Register 32 = 0x0000`
  - возвращает `Register 33 = 0x0000`
  - снова запирает stimulation path
- после `close()` режим контроллера сбрасывается в `unknown`

Восстановление режимов:

- после `measure_impedance` контроллер больше не переинициализируется безусловно в stimulation mode
- теперь после измерения восстанавливается исходный режим:
  - если до измерения был `stimulation`, возвращается `stimulation`
  - если был `recording`, возвращается `recording`
  - иначе сохраняется предыдущее логическое состояние

Синхронизация профилей:

- в `rhs2116_profiles.py` профиль `recording` переведен на широкополосные значения:
  - `Register 1 = 0x051A`
  - `Register 4 = 0x0016`
  - `Register 5 = 0x0017`
  - `Register 6 = 0x00A8`
  - `Register 7 = 0x000A`

Ожидаемый эффект:

- обычные safe-команды TCP больше не включают stimulation path
- после остановки стимуляции чип возвращается в безопасное состояние
- переходы `recording -> stimulation -> recording` остаются рабочими
- риск перегрузки по питанию из-за случайно оставленного stimulation-ready состояния снижен
